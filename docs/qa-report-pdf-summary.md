# PDF 요약 앱 — QA 리포트

- 대상: Task 1~7로 완성된 전체 앱 (`app/`, `components/`, `lib/`)
- 테스트 방식: `npm run dev`로 로컬 서버 기동 후 `curl`로 API 8개 시나리오 검증 + Playwright(Chromium, headless)로 브라우저 UI 흐름 검증
- 테스트 PDF: 모두 영어 텍스트, `cupsfilter`로 생성(`textutil`은 이 macOS에서 PDF 출력 미지원)
- 실행일: 2026-07-28

## 요약

API 8개 시나리오(정상 경로, 빈 PDF, 비-PDF 파일, 초단문 PDF, 페이지 수 초과, 용량 초과, 무료 모델 폴백, 브라우저 UI 전체 흐름)를 모두 실행했고, **8개 전부 첫 실행에서 기대대로 통과**했다. 코드 수정이 필요한 버그는 발견되지 않았다. 다만 로그 노이즈성 경고 1건과 이미 알려진 모델 응답 변동성(언어 미준수) 1건을 관찰했으며, 둘 다 기능적 실패로 이어지지 않아 Minor/관찰 사항으로만 기록한다.

## 발견한 이슈 (심각도순, 수정 여부 포함)

**Critical/Major: 없음**

1. **[Minor] (관찰, 수정 안 함) PDF 처리 중 `Math.sumPrecise is not a function` 경고 로그**
   - 재현 조건: `/api/summarize`에 유효한 PDF를 업로드할 때마다 dev 서버 로그에 `Warning: TypeError: Math.sumPrecise is not a function`가 반복 출력됨.
   - 원인: `unpdf`가 내장하는 pdf.js 번들(`node_modules/unpdf/dist/pdfjs.mjs`)의 폰트/XFA 관련 유틸리티 코드가 `Math.sumPrecise`(비교적 최신 V8 API)를 호출하는데, 이 코드가 이 프로젝트 코드 경로가 아니라 pdf.js 내부에서 자체적으로 캐치되어 "Warning"으로만 로그되고 요청은 정상 처리됨(응답은 계속 200, 추출된 텍스트도 정상).
   - 영향: 없음 — 모든 정상/에러 경로 응답이 기대대로 동작함을 재확인함(시나리오 1, 4에서 재확인). 순수 로그 노이즈.
   - 조치: 서드파티 라이브러리(pdf.js) 내부 코드이며 우리 애플리케이션 코드 경로에 없어 수정하지 않음. Node 버전 업그레이드 또는 `unpdf` 업데이트 시 자연 해소될 가능성이 있음. 배포 환경(Node 버전이 다를 수 있음)에서 재확인 권장.

2. **[Minor] (관찰, 수정 안 함) 무료 모델이 한국어 대신 영어로 응답하는 경우 발생**
   - 재현 조건: `AI_DEBUG=1`로 재기동 후 정상 PDF(영어 본문) 업로드 시, 1순위 모델(`google/gemma-4-31b-it:free`)이 429로 실패해 2순위 모델(`openai/gpt-oss-20b:free`)로 폴백했고, 이 2순위 모델이 `summary`/`points`를 한국어가 아닌 **영어**로 반환함(시스템 프롬프트는 한국어 출력을 명시함에도).
   - 영향: 응답은 여전히 200이고 JSON 스키마(`summary` 문자열, `points` 배열)는 유효함 — 기능적으로는 정상 동작. 다만 최종 사용자가 기대하는 "한국어 요약"이 아닐 수 있음.
   - 조치: 무료 모델의 지시사항 준수(instruction-following) 편차이며, 결정론적으로 고칠 수 있는 코드 결함이 아님(Task 5에서도 동일 현상이 이미 관찰됨). 코드 수정 없이 관찰 사항으로만 기록.

3. **[정보] 시나리오 4(초단문 PDF)에서 모델이 "내용 없음" 취지의 메시지를 요약으로 반환**
   - 재현 조건: 본문이 `"Short."` 한 단어뿐인 PDF를 업로드하면, 모델이 실제 내용을 요약하는 대신 "문서 본문이 제공되지 않았다"는 취지의 `summary`/`points`를 생성함.
   - 영향: 브리프의 기대 결과(`200`, 에러 없이 `summary`/`points` 반환)는 정확히 충족함 — 실패가 아님. 다만 극단적으로 짧은 입력에서는 모델이 "요약할 내용이 없다"고 판단하는 경향이 있다는 점을 참고용으로만 남김. 코드 변경 불필요.

[^1]: "빈 PDF" 픽스처는 실제로는 0바이트가 아니라 공백 문자 1개짜리 텍스트 파일을 `cupsfilter`로 변환한 PDF다. `cupsfilter`는 진짜 0바이트 입력 파일은 MIME 유형을 판별하지 못해 변환 자체를 거부하므로(`cupsfilter: MIME 유형을 결정할 수 없습니다` 에러), 공백 문자 1개를 사용했다. 이 PDF도 `lib/pdf/extract.ts`의 `.trim()` 이후에는 추출 텍스트가 빈 문자열이 되므로, 진짜 빈 PDF와 동일한 코드 경로를 그대로 검증한다.
[^2]: 이 시나리오는 이 QA 태스크(Task 8) 실행 당시의 `lib/ai/summarize.ts` 기준으로 통과했다. 이후 최종 전체 브랜치 리뷰에서 "points 3~5개" 요건이 검증되지 않는 문제(Finding #4)가 발견되어 `extractValidPoints`/`isValidParsed`가 3개 미만인 응답을 더 이상 유효로 보지 않도록 수정되었다(커밋 `e53157c`). 즉 이 표의 "points 2개" 응답은 **현재 코드 기준으로는 유효 응답으로 받아들여지지 않고, 폴백 체인의 다음 무료 모델로 자동 재시도된다.** 이 변경 이후 시나리오 1을 실제로 재실행해 재확인하지는 않았다 — 재확인이 필요하면 정상 PDF로 `/api/summarize`를 다시 호출해 `points.length >= 3`을 직접 확인할 것.

보너스로 "PDF로 위장한 손상 파일"(MIME은 `application/pdf`, 실제 내용은 임의 텍스트)도 업로드해 `lib/pdf/extract.ts`의 예외 처리 경로를 확인했다 — 500 크래시 없이 400 `이 PDF에서 텍스트를 추출할 수 없습니다.`로 정상 처리됨(추가 확인, 브리프에 명시된 8개 시나리오는 아님).

## 검증 범위

**확인한 것:**
- API 레벨: 정상 경로, 빈 PDF, 비-PDF 파일, 초단문 PDF, 20페이지 초과, 4MB 초과, 무료 모델 폴백(부분 실패, 전체 실패 양쪽), 응답 상태 코드와 에러 메시지 문자열 정확성
- `.env`의 `OPENROUTER_API_KEY`를 일시적으로 빈 문자열로 바꿔 "전체 무료 모델 실패" 상황을 흉내내고, 502 + 명확한 한국어 에러 메시지(스택트레이스, raw 500 없음)를 확인한 뒤 원래 키로 정확히 복원(`diff`로 무변경 확인)
- 브라우저 UI: idle → processing → result/error 4개 상태 전환, 클릭 업로드, 비-PDF/페이지초과 에러 메시지 표시, "다시 시도"/"다른 PDF 요약하기" 버튼으로 idle 복귀, Tab 키보드 포커스 이동, 콘솔 JS 런타임 에러 없음(Task 7에서 이미 드래그앤드롭, 모바일 반응형은 별도로 검증됨 — 이번 태스크에서는 브리프 지정 파일 3종의 클릭 업로드 흐름 위주로 재확인)
- MIME은 `application/pdf`이지만 실제로는 손상된 파일 업로드 시 예외 처리 경로(보너스)
- 최종 `npm run build`, `npx tsc --noEmit`, `npm run lint` 모두 에러 없이 통과
- `git log --all --full-history -- .env` 출력 없음(`.env`가 어떤 커밋에도 포함되지 않음) 확인

**확인하지 못한 것(범위 밖 또는 로컬 환경 제약):**
- 한글(CJK) PDF 텍스트 추출 — 이 macOS의 Node v26.5.0 `fetch()`가 `file://`를 지원하지 않아 로컬에서 깨짐(기존에 확인된 정책상 배포 후 검증 예정, 이번 QA 범위 아님)
- 동시 다중 요청(동시성) 부하 상황에서의 동작 — 이 앱은 인증, DB가 없는 stateless 도구라 계정/동시성 경합 이슈 자체가 구조적으로 적으나, 별도의 동시 요청 부하 테스트는 수행하지 않음
- OpenRouter 쪽의 실제 네트워크 타임아웃(느린 네트워크 등) 시뮬레이션 — 코드상 10초 타임아웃(`TIMEOUT_MS`)이 있는 것은 확인했으나 실제로 타임아웃을 트리거해보지는 않음(무료 모델 API가 원격 서비스라 인위적으로 느리게 만들기 어려움)
- 실제 브라우저(Chrome/Safari/Firefox 등 헤드리스가 아닌 환경)에서의 육안 확인 — Playwright headless Chromium으로만 확인했으며 실제 사용자 브라우저 환경 확인은 하지 않음
- 여러 페이지, 표/이미지가 섞인 실제 업무 문서(계약서, 논문 등) 기준의 요약 품질 평가 — 이번 QA는 에러 처리, 경계값 위주이며 요약 "품질"(정확성, 유용성) 자체는 평가 범위 밖
