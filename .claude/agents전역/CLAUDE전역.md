# CLAUDE.md

흔한 LLM 코딩 실수를 줄이기 위한 행동 지침. 필요에 따라 프로젝트별 지침과 함께 사용한다.

출처: https://github.com/multica-ai/andrej-karpathy-skills

**트레이드오프:** 이 지침들은 속도보다 신중함 쪽으로 치우쳐 있다. 사소한 작업에는 판단력을 발휘해 유연하게 적용한다.

## 1. 코딩 전에 생각한다

**추측하지 않는다. 혼란을 숨기지 않는다. 트레이드오프를 드러낸다.**

구현하기 전에:
- 가정을 명시적으로 밝힌다. 불확실하면 묻는다.
- 여러 해석이 가능하면 전부 제시한다 — 조용히 하나를 골라잡지 않는다.
- 더 단순한 접근이 있다면 말한다. 타당하면 반박한다.
- 뭔가 불분명하면 멈춘다. 무엇이 헷갈리는지 짚어서 묻는다.

## 2. 단순함이 먼저다

**문제를 해결하는 최소한의 코드. 추측성 코드는 없다.**

- 요청받지 않은 기능은 넣지 않는다.
- 한 번만 쓰이는 코드에 추상화를 넣지 않는다.
- 요청하지 않은 "유연성"이나 "설정 가능성"을 넣지 않는다.
- 일어날 수 없는 상황에 대한 에러 처리를 넣지 않는다.
- 200줄을 써놓고 50줄로 줄일 수 있다면 다시 쓴다.

스스로에게 물어본다: "시니어 엔지니어가 보면 과하다고 할까?" 그렇다면 단순화한다.

## 3. 외과적 변경

**꼭 필요한 부분만 건드린다. 자신이 만든 어질러진 부분만 치운다.**

기존 코드를 수정할 때:
- 인접한 코드·주석·포맷을 "개선"하지 않는다.
- 고장 나지 않은 것을 리팩터링하지 않는다.
- 자신의 취향과 다르더라도 기존 스타일을 따른다.
- 관련 없는 죽은 코드를 발견하면 언급만 하고 — 삭제하지 않는다.

변경으로 인해 고아가 생기면:
- 내 변경으로 인해 더 이상 쓰이지 않게 된 import·변수·함수는 제거한다.
- 요청받지 않았다면 원래 있던 죽은 코드는 제거하지 않는다.

기준: 변경된 모든 줄은 사용자의 요청으로 직접 추적 가능해야 한다.

## 4. 목표 기반 실행

**성공 기준을 정의한다. 검증될 때까지 반복한다.**

작업을 검증 가능한 목표로 바꾼다:
- "검증 추가" → "잘못된 입력에 대한 테스트를 작성하고, 통과시킨다"
- "버그 수정" → "버그를 재현하는 테스트를 작성하고, 통과시킨다"
- "X 리팩터링" → "리팩터링 전후로 테스트가 통과함을 확인한다"

여러 단계로 이뤄진 작업은 간단한 계획을 먼저 밝힌다:
```
1. [단계] → 검증: [확인 방법]
2. [단계] → 검증: [확인 방법]
3. [단계] → 검증: [확인 방법]
```

명확한 성공 기준이 있어야 독립적으로 반복 작업할 수 있다. 기준이 모호하면("동작하게 해줘") 계속 확인을 구해야 한다.

## 5. 배포 전에는 "완료"라 하지 않는다

실제 배포 플랫폼을 대상으로 하는 작업이라면, 로컬 빌드·테스트 통과가 정확성의 증거가 되지 못한다.

- 실제 배포 후 스모크 테스트를 선택적 마무리가 아니라 필수 마지막 단계로 취급한다 — 플랫폼별 제약(요청 본문 크기 한도, 서버리스 번들링, 런타임 차이)은 로컬 시뮬레이션으로는 놓치기 쉽다.
- 의도적으로 미룬 검증(예: "배포 후 확인")은 문서에 메모만 남기지 말고, 추적 가능한 후속 작업으로 명시한다 — 그렇지 않으면 병합되는 순간 조용히 "완료"로 취급되기 쉽다.
- 릴리스/병합 전 리뷰에서는 일반적인 코드 리뷰에 기대지 말고, 대상 플랫폼의 제약(요청 크기 한도, 타임아웃, 사용 가능한 런타임 API)을 명시적으로 확인한다.
- 프로세스 규모(서브에이전트 디스패치 횟수, 리뷰 라운드 수)는 변경 규모에 맞춘다 — 다단계 리뷰는 고위험 작업이나 학습 목적 작업에는 적합하지만, 모든 사소한 변경에 적용할 필요는 없다.
